# 席次まるっと（Sekiji Marutto）

ゲスト名簿・出欠管理・席次表を、ひとつのデータでつなぐ結婚式準備Webアプリです。
招待状への回答が出欠に、出欠が出席者だけの席次表づくりに、そのまま流れていきます。

🔗 **公開デモ**: https://tytanaka.github.io/sekiji-marutto/

## なぜ作ったか

### 課題：式場が決まった「あと」の準備は、いまだに手作業が多い

式場探しのサービスは充実していますが、式場が決まった後の準備（招待状の回答集め、出欠の集計、席次表づくり）は、
紙の名簿やExcelに頼る場面が多く残っています。作業ごとに同じゲスト情報を転記するため、手間とミスが生まれます。

便利な準備ツール自体は存在しますが、その多くは**式場が導入して新郎新婦に提供する業務用システム**です。
つまり「使えるかどうかは式場次第」で、レストランウェディングや小規模な式場、二次会などでは手作業が残りやすいのが現状です。

### 解決：式場に依存しない、「1人のゲスト = 1レコード」の準備アプリ

本アプリは式場を介さず、新郎新婦が直接・無料で使える形を取りました。
**1人のゲスト = 1レコード** を貫き、招待リンクへの回答が出欠に、出欠が出席者だけの席次表づくりに、
印刷用レイアウトにまでそのまま流れる設計で、転記そのものをなくすことを目的にしています。

- 式場フリー：どの式場でも、式場が決まる前からでも使える
- 一気通貫：回答 → 席次候補 → 集計 → 印刷がひとつのデータでつながる
- 日本の式次第への配慮：上座の概念や新郎側/新婦側の区別を、自動配置のルールに組み込んでいる

### 検証しながら作ったこと

- 120名・15卓の大規模サンプルで、表示・自動配置・印刷が破綻しないことを自動テストで確認
- 実際の印刷（A4）を想定し、紙に出力した状態をPDFで目視確認しながらレイアウトを調整
- ゲスト側の回答ページは、年配のゲストも想定して文字サイズとコントラストを専用に調整
- 友人に実際に触ってもらい、「トップページで何のアプリか分からない」「ログインが常時表示されている」
  という情報設計への指摘を受けて、初回トップページとログイン導線を設計し直した

## 主な機能

- **トップページ**: 初回訪問時は「できること」を説明し、サンプルで試してから使い始められます（再訪時は直接アプリへ）
- **ダッシュボード**: 回答率・出席/欠席/未回答の集計、卓ごとの充足状況、「次にやること」の提示
- **ゲスト管理**: 検索・絞り込み（新郎側/新婦側、出欠状態）、追加・編集・削除、アレルギー・同伴者・メモの管理
- **出欠管理**: ワンタップで 出席/未回答/欠席 を切替。出席でなくなったゲストは席次から自動で外れます
- **席次表エディタ**: 円卓レイアウト（上座マーカー付き）、ドラッグ＆ドロップ／タップの両対応、
  定員・重複配置のバリデーション、全員配置完了の検出
- **Web招待状プレビュー＋ゲスト回答体験**: 式情報の表示、開催日カウントダウン、
  ゲスト側の回答フォーム（回答は名簿・席次表へ即時反映）
- **印刷ビュー**: 卓ごとの席順リスト、印刷用レイアウト最適化
- **変更レーダー**: ゲストの回答内容（出欠・同伴者・アレルギー）の変更を検知して一覧表示。クラウドではゲスト本人の回答もリアルタイムに届きます
- **競合調査メモ（2026年10月）**: 国内の主要な同種サービス（Dear Guest、Weddingday、Concept Marry、ブラプラ、Favori、PIARY など）の公開情報を調査した範囲では、招待リンクの開封確認・席次の自動配置と理由説明・作法チェック・提出時の変更差分は確認できませんでした。逆に当日受付チェックインや回答変更の通知は他社にもあるため、本アプリの差別化の軸は前者の4点に置いています
- **自動配置の理由表示**: 自動席次提案のあと、配置理由（上座配慮・同じ側/グループなど）を卓ごとに説明します
- **開封トラッキング**: 招待リンクが開封されたかを記録し、「開封したのに未回答」のゲストだけを絞って、見た前提の柔らかい催促文でフォローできます（クラウドでは `get_invitation` RPC が開封を記録）
- **席次作法チェック**: 役職者の下座配置・親族の末席・上座の空席など、日本の披露宴の作法の観点で席次表を自動校正します
- **式場提出パック**: 席次表＋ゲスト一覧（アレルギー等）に加え、提出時点を記録しておくと「前回提出からの変更差分」付きで印刷できます。ゲスト一覧・席次表の CSV ダウンロードにも対応（Excel で受け取りたい式場向け）
- **当日受付モード**: 挙式当日、受付で出席ゲストを卓順に表示し、タップで到着チェック。アレルギー表示と到着進捗つき
- **ゲストへのお席表示**: 席次が決まったら、ゲスト本人の招待ページに「お席のご案内（卓・席番号）」が表示されます
- **初期設定**: サンプルのまま始めず、最初に自分たちの式の情報（名前・日付・会場）を入れて、ゲストを空にした状態からでも開始できます
- **モバイル最適化**: スマホでは主要タブを下部固定バーに配置し、当日受付などの主要機能へ片手で届くようにしています
- **自動保存**: すべての変更はブラウザに自動保存され、再訪時に復元されます

## 技術構成と設計判断

| 領域 | 選定 | 理由 |
| --- | --- | --- |
| 言語/基盤 | TypeScript + React 18 + Vite | 型安全なUI開発の標準構成。高速な開発体験 |
| 状態管理 | useReducer + Context | 依存を増やさず、状態遷移（reducer）を純粋関数としてテスト可能に |
| ドメイン層 | `src/lib/` に純粋関数を分離 | 席座標計算・配置バリデーション・集計をUIから切り離し単体テストで担保 |
| 永続化 | localStorage（バージョン付きスキーマ＋検証） | バックエンドなしで完結させ、読み込み時は不正データを弾いて初期化 |
| テスト | Vitest + Testing Library（53件） | ロジックだけでなく、画面遷移のスモークテストと120名規模の検証まで自動化 |
| 配色/タイポ | デザイントークン（CSS変数）で一元管理 | 状態色（出席/未回答/欠席）を全画面で統一し、一貫した体験に |

### ディレクトリ構成

```
src/
  types.ts            ドメインモデルと表示ラベル
  lib/                純粋関数（席配置計算・集計・初期データ）と単体テスト
  store/              reducer + 永続化（状態遷移のテスト付き）
  components/         画面コンポーネント（ダッシュボード/ゲスト/席次/招待状/印刷）
docs/SPEC.md          本番仕様
```

### こだわった点

- **席次のバリデーションをドメイン層で一元化**：UIの操作ミスではなく「状態として不正」を防ぐ設計
- **アクセシビリティ**：タブのARIA対応、44px以上のタップ領域、キーボードでも操作できる席選択、
  `prefers-reduced-motion` 対応
- **レスポンシブ**：スマホでは席次エディタがタップ配置で完結するよう設計

## UX改善の記録

公開後に実際の操作監査（全タブの操作・ドラッグ配置・回答送信まで）を行い、以下を改善しました。

- 招待回答フォームの初期選択を廃止し、明示的に選ぶまで送信できないように（誤回答の防止）
- 席の配置解除を2段階タップに変更し、誤タップで席次が崩れないように
- 出欠変更で席が外れる場合は事前確認を表示
- コントラスト強化（統計の数字、補助テキスト、アレルギー情報は警告色＋太字に）
- 席ボタンの拡大と氏名の2行表示、席番号の明示、選択状態の視認性向上
- 概要のヒントをボタン化し、未回答ゲスト一覧へ直接遷移
- 「式の情報」を設定タブへ分離、印刷ビューは空席を集約し未配置ゲストを名前で表示

## 競合調査・運用監査と改善（2026-10-31）
- **競合調査**: 国内の主要な同種サービス9社超の公開情報を調査し、開封確認・席次の自動配置と理由説明・作法チェック・提出時の変更差分が未提供であることを確認（詳細は「主な機能」の競合調査メモ）。この4点を差別化の軸として実装した
